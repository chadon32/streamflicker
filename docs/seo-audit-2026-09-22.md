# StreamFlicker SEO implementation and evidence

Audit and local verification: September 22, 2026 (America/Phoenix).
Canonical site: https://www.streamflicker.com/.
Research market: English-language US queries, inferred from the app's default US availability region. This is a working market assumption, not a claim that the business operates only in the US.

## Outcome and release scope

Implemented a focused technical/content SEO pass: generated initial homepage content; real, script-free About and movie-night guide pages; central metadata/canonicals; a three-URL sitemap; query/preview indexing rules; genuine 404 behavior; and tested links into search and the planner.

Prepared on `codex/seo-foundations-2026-09-22` for GitHub push. Production deployment and merge to `main` are intentionally not part of this pass: the brief requires separate production approval. Local checks do not prove Google indexing, rankings, traffic gains, or a deployed Vercel routing change.

GitHub `main` began at `bb93930`, while the workspace already contained substantial website, iOS, and video work. Commit `62c98c5` preserves the existing website/API/build/test baseline, including the existing account-deletion implementation required by its regression tests. These were not SEO improvements authored in this pass. New SEO work is a separate commit. Native Xcode/EAS files, videos, screenshots, credentials, and older untracked release documents were left out; the branch is a web release candidate, not a complete iOS release snapshot.

## Confirmed product and conversion model

StreamFlicker is a movie-discovery application, not a streaming host. Code and browser usage confirm title/actor/theme search, focused shortcuts, family/date/quick-watch modes, trailers, a movie-night planner, local watchlists, and provider availability links. The bundled catalog has 1,799 records; this is not evidence of every movie or accurate metadata for every record.

Meaningful conversions: open a relevant trailer, save a shortlist or movie night, and check a title's current provider availability. Optional affiliate destinations, support, newsletter, sponsorship, and AdSense configuration exist. Their presence does not prove approval, revenue, or purchase attribution. Native monetization and account policy were not changed.

No Google Search Console, GA4, Bing Webmaster, or paid keyword connector was available in tool discovery. No authenticated analytics property was inspected. Repository inspection found no pageview analytics integration; the optional affiliate analytics helper has no call sites. No new tracker, cookie, external telemetry endpoint, or recurring expense was added.

## Implementation details and route policy

- `src/seo/pages.ts`: canonical origin, titles/descriptions, three indexable paths, WebSite/WebPage/AboutPage and guide breadcrumb data. No fabricated ratings, reviews, prices, offers, credentials, SearchAction, or FAQ rich-result promise.
- `src/seo/PageSeo.tsx`: shared browser/static metadata and JSON-LD, escaped for safe embedding.
- `src/seo/render.tsx`, `StaticHome.tsx`, `scripts/generate-seo.mjs`: static generation using existing Vite/React dependencies. The renderer runs only at build time. No full catalog gets embedded in informational HTML.
- `src/main.tsx`: removes only owned seed metadata before React 19 takes over. Helmet 3 on React 19 emits native metadata; legacy SSR context extraction is not supported. Initial and rendered single-tag behavior were both checked.
- `src/App.tsx`: guide route for development, context links, query-backed search, planner deep link. Planner entry waits for account/storage initialization; history rate limits cannot break typing. Auth/security state reset behavior is preserved.
- `BusinessPage.tsx`: shared metadata handled by wrapper; skip link, guide link, compact mobile header, responsive image sources, decorative backdrop alt text.
- `MovieNightGuide.tsx`, `DiscoveryExplainer.tsx`: existing dark/rose visual system, readable hierarchy, no new animations; guide breadcrumbs, native details/summary FAQ, 44px FAQ/footer targets and clear CTAs.
- `vercel.json`: clean URLs, trailing-slash normalization, `/business` -> `/about` permanent redirect, no catch-all rewrite. Root `q`, `movie`, `plan` query variants and API responses receive noindex headers. These keys describe app-root states, not every arbitrary query appended to static pages; informational query variants consolidate through their canonical.
- `robots.txt` points to the generated sitemap. Only `/`, `/about`, `/movie-night` enter it. No invented `lastmod` dates. Query states, duplicate aliases, error pages, and dialogs are excluded.
- Vercel preview builds stay noindex before and after React starts. No robots blocking was added that would prevent crawlers from reading noindex. Authentication remains the security boundary, not robots.txt.
- `.vercelignore` explicitly includes the new generator/config. Production routing still needs edge verification after an approved deployment; the local routing mirror is not a Vercel deployment.

No large-image social card is claimed without a suitable approved image. Social titles/descriptions/URLs and a summary card are provided; a branded raster sharing asset remains a follow-up.

## Remaining risks, access, and rollback

1. **Catalog accuracy is the largest unresolved trust issue.** Browser examples contained questionable ratings/runtimes and non-movie records. The family <=100-minute combination produced no picks. A content caveat is not a substitute for correcting source data; do a dedicated ID/certification/runtime/trailer audit before publishing movie-level SEO pages or promoting family-safety claims.
2. Search Console property verification/access and analytics property selection are needed for actual organic performance and conversion reporting. No existing high-traffic pages could be identified from analytics; known URLs were preserved.
3. Production deploy approval is required. Then verify Vercel edge redirects, canonical host variants, noindex headers, static HTML, current availability API, and Google URL Inspection. Submit the sitemap through the verified property; do not claim immediate indexing.
4. Legal/privacy pages remain modals. Consider crawlable equivalents with the same approved text and existing modal access, after business/legal confirmation. No legal terms were rewritten.
5. Keep consistent public links to the selected www origin. No DNS/domain changes or external messages were made.
6. Roll back the SEO commit as a unit (generator/build command/routing/components are coupled). Keep the pre-existing website baseline commit. Do not revert, overwrite, or delete the user's unrelated dirty native/video work.

## 30 / 60 / 90-day roadmap

### Days 1-30: correctness and measurement

Approve/review the branch, deploy only when authorized, and verify actual edge behavior. Correct the highest-risk rating/runtime/trailer metadata with authoritative IDs and regional certification sources. Obtain Search Console and a single analytics destination, establish a 28-day baseline, and record the actual release date. Run repeated mobile/desktop Lighthouse or equivalent labs and inspect field CWV if sufficient traffic exists. Prioritize the large homepage catalog and font delivery using those results.

### Days 31-60: content and conversion quality

Use actual query/impression data to refine the existing homepage and guide, not generate variants. Create one curated zombie guide only if verified examples, editorial selection criteria, useful distinctions and current availability caveats justify it. Add an approved branded social image. Measure guide -> planner -> saved shortlist/provider exit, and test a clearer primary CTA without disturbing browsing. Improve keyboard/mobile issues uncovered by a fuller accessibility audit.

### Days 61-90: evidence-led expansion

Only build standalone title/collection pages when provenance, freshness, true 404s and enough unique content are reliable. Use region-aware provider information rather than blanket platform promises. Evaluate which guide/search cohorts actually produce useful actions. Explore legitimate editorial mentions through original curation or a documented movie-night tool; no paid links, spam outreach, or unauthorized third-party contact.

## Measurement plan

- Search Console: weekly export organic clicks, impressions, CTR and average position by canonical landing page, query, country and device. Separate brand/nonbrand and instructional/discovery intents. Do not treat average position as a business outcome.
- Analytics, after selecting/authorizing one destination: organic landing sessions and deduplicated `planner_open`, `planner_saved`, `watchlist_add`, `trailer_open`, `availability_outbound`. Do not log raw search text, email, account IDs or full query strings unnecessarily. Honor existing consent and avoid duplicate integrations.
- Conversion rate: organic sessions with at least one chosen meaningful action / eligible organic landing sessions. Report individual funnel steps and unique converted sessions, not a sum of clicks. Affiliate revenue requires program-side attribution; an outbound click is not a sale.
- Compare 28-day pre/post windows with matching weekdays, country/device and landing-page cohorts. Also inspect prior-year periods where available, release schedule/seasonality, concurrent catalog changes and other marketing. Low samples are inconclusive, not failures or wins.
- Record the real production release date separately from this audit/branch date. Recheck crawl/index coverage after release, then weekly; no unsupported ranking guarantee.

## Official implementation references

The rendering and link strategy follows [Google's JavaScript SEO guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics): useful response HTML and real anchor links improve discoverability, while status codes and index directives still matter. Canonical and sitemap decisions follow [canonicalization guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) and [sitemap construction guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

Static rendering uses [React renderToStaticMarkup](https://react.dev/reference/react-dom/server/renderToStaticMarkup) and the existing [Vite SSR build capability](https://vite.dev/guide/ssr.html), without treating static markup as hydrated UI. Routing and query header configuration follow [Vercel's documented project configuration](https://vercel.com/docs/project-configuration/vercel-json).

Schema is limited to verified identity/page structure under [Google's structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [site-name guidance](https://developers.google.com/search/docs/appearance/site-names), and [breadcrumb requirements](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb). JSON syntax and required shape were checked locally. Google Rich Results Test and Search Console live validation remain post-deployment checks; valid markup is not a promise of rich-result display.
